# 校园二手 · 交易与任务平台

一个给同学用的轻量交易平台：**闲置物品交易** + **跑腿/帮忙任务发布**。

核心思路：**平台不经手资金，只做信息撮合 + 信用约束。**

---

## 为什么不做支付

最初的想法是做一个"钱先托管、确认后放款"的系统（类似闲鱼担保）。

后来想清楚了要放弃这个方向，原因有两条：

**第一，法律上行不通。** 平台代收代付资金、让钱在平台账户停留，
个人开发者没有支付业务资质，这会触及「资金池」相关的红线。
哪怕只是"收保证金"，只要钱进了平台账户，性质就变了。

**第二，也是更重要的 —— 这个场景真正缺的不是支付。**

想一下学生之间的二手交易：

- 支付？微信扫码两秒钟的事，**不需要平台代劳**
- 真正的问题是 **信任** —— "我付了钱你不发货怎么办"

而支付解决的恰恰是信任问题中最容易的那部分（钱怎么走），
最难的那部分（**这个人靠不靠谱**）支付根本管不了。

**所以这个项目转而做两件事：**

| 做什么 | 解决什么 |
|---|---|
| **学号实名** | 让你知道对面是谁 —— 跑得了和尚跑不了庙 |
| **信用记录** | 让"放鸽子""货不对板"变成有代价的事 |

同学圈子很小，一个"收钱不发货"的记录，比任何保证金都有威慑力。

## 现在做到哪一步了

### ✅ 第一阶段：账本核心（`src/ledger/`）

**这一块是能力储备，当前主线没用上。**

做的是"钱怎么算不出错"——如果将来要做企业版或真接支付，这是基础。
34 项测试全过。

防住的坑：

| 坑 | 防法 |
|---|---|
| 余额被扣成负数 | SQL 里 `WHERE (balance - frozen) >= 金额` |
| 同一订单重复扣款 | 订单号主键 + 流水表 `UNIQUE(order_id, action)` |
| 重复结算 | 结算前校验订单状态 |

### ✅ 第二阶段：交易核心（`src/trade/`）—— **当前主线**

不做钱，只做"事到哪一步了" + "谁守约"。40 项测试全过。

**核心是一张状态机，两条业务线共用：**

```
open ──take──→ taken ──deliver──→ delivering ──confirm──→ completed
  │              │                    │
  └──cancel──→ cancelled              └──dispute──→ disputed ──resolve──→ 终态
```

闲置交易和跑腿任务的**流程完全一样**，只是叫法不同：

| 步骤 | 闲置交易 | 跑腿任务 |
|---|---|---|
| take | 买家拍下 | 有人接单 |
| deliver | 卖家发货 | 接单者完成 |
| confirm | 买家确认收货 | 发布者验收 |

**三张表：**

- `users` —— 用户，学号唯一，有学号即视为已实名
- `trades` —— 交易单，`kind` 区分物品/任务，`status` 走状态机
- `trade_events` —— 事件流水，**追加式、不可改不可删**，出纠纷可完整回放
- `credit_events` —— 信用记录，谁守约谁放鸽子

### ✅ 第三阶段：能用了（`src/server/` + `public/`）

一个**零依赖**的网页服务 —— 只用 Node 自带的 `node:http` 和 `node:sqlite`，
不装 Express、不装任何东西。9 组接口实测全过。

**为什么不用框架？** 因为你现在还在"看懂"的阶段。
Express 帮你把请求链路藏起来了，藏起来的东西你没法学。
用 `node:http`，你能亲眼看到"一个请求进来 → 路由匹配 → 读数据库 → 回 JSON"的完整路径。
等这条链路你闭着眼都能画出来，再上框架是提效；现在上框架是遮蔽。

**身份暂时很简化：** 发布时手填昵称 + 学号，系统自动建档；填了学号就算实名。
密码、短信验证这些都还没有 —— 先把"平台是活的"做出来，身份系统是下一步。

```bash
node src/server/server.js     # 起来后打开 http://localhost:3000
node tests/api.test.js        # 9 组接口实测（需服务已启动）
```

### ✅ 第四阶段：身份审核（`src/identity/`）

甲路线（纯撮合）平台不经手钱，唯一能约束用户的就是**信用**。
而信用体系的前提是——**这个人是谁，他说的话算不算数**。
没有身份，信用分就是记在一个虚构昵称上，毫无威慑力。

所以审核机制不是附加功能，**是甲路线能不能立住的地基。**

**审核机制拆成四层，本次做第一层：**

```
审核机制
├── 1. 身份凭证      你凭什么是我们学校的人？   ← 本次做了这层
├── 2. 信用原始积累   这个人历史上守不守约？
├── 3. 违规判定      什么算违规？谁来判？
└── 4. 处置手段      扣分？禁言？拉黑？
```

**为什么没做人脸识别？** 两个原因：

1. **位置错了。** 人脸识别的独特价值是「防冒用」，而防冒用要在
   「外校人混进来」和「同学号被误填」都被解决之后才用得上。
   门口还没装锁就先装金库门，顺序不对。
2. **个人开发者接不到底库。** 人脸比对要有权威源（公安/教育部核验 API），
   需要企业资质；另一个选择是自存人像比对，那就变成**存敏感个人信息**，
   合规成本高一个量级。

**核心业务规则：手滑 vs 真冒用**

老板选了「受理 + 人工裁定」，但如果不加过滤，手滑填错学号的人会全涌进人工队列。
观察：**手滑的人不会精确地知道你叫什么名字。**

| 情形 | 学号 | 姓名 | 判定 |
|---|---|---|---|
| 正常 | 2315402125 | 何孝彬 | 学号无主 → 自动通过 |
| 手滑 | 2315402125 | 张三 | 学号有主 + 姓名不符 → **挂起**（可批量通知改） |
| 真冲突 | 2315402125 | 何孝彬 | 学号有主 + 姓名一致 → **进人工队列** |

「姓名是否也撞上」是个免费过滤器，能在进人工之前自动分掉一半。

**待审状态下能干什么 —— 老板拍的分界线：**

| 能做 | 不能做 |
|---|---|
| ✅ 浏览（零风险、高价值——他看，你就赢得了审核他的时间） | ❌ 发布 / 接单（会产生责任的行为，没确认身份的人不配产生责任） |

**架构决策：为什么不改 `users` 表**

`users` 被 `trades` / `trade_events` / `credit_events` 三张表外键引用着，动它等于动地基。
而需求是「学号可能被两人同时声称」，跟 `users.student_no` 的 UNIQUE 直接冲突。

解法是把「声称」独立成表：

| 表 | 管什么 |
|---|---|
| `users` | 只管**已确认身份的人**，`student_no` 保持唯一（**未改动**） |
| `identity_claims` | 所有**声称**，含待审/挂起/已通过/被驳回（新增） |
| `identity_events` | 审核流水，**追加式**，谁在何时基于什么把谁判成了什么（新增） |

关键防线是一个**部分唯一索引**，它保证「一个学号只能有一条已通过的声明」：

```sql
CREATE UNIQUE INDEX idx_claim_verified_unique
  ON identity_claims(student_no)
  WHERE status = 'verified';
```

### ⚠️ 本阶段踩的两个坑

**坑 1：学号对上就直接放行，姓名压根没比（端到端测试抓出）**

第一版逻辑是「按学号查已通过的主人，查到就认成本人」。
测试场景 2 用手滑撞号立刻暴露：**只要知道同学号，随便填个名字就能顶替**，实名形同虚设。
修法：查到主人后**必须再比一次姓名**，姓名不符走冲突流程。

**坑 2：自检规则把合法情况误报成问题**

`audit()` 原先假设「是终态就该有审核人」，但**自动通过根本没有人类审核员**——
于是合法的自动通过被报成「缺审核人」4 条。
这很危险：**天天报假警的报警系统，真出事时没人看。**
修法：机判的声明 `reviewed_by` 记为 `system:auto`，跟人判的区分开，自检规则相应收紧。

### ⚠️ 一个必须说清楚的「设计边界」（不是漏洞）

场景 3 暴露的：**学号 + 姓名都一致时，系统认成本人放行。**

那如果真是冒用者呢？——**系统区分不了。**

在没有密码、没有登录态的前提下，「本人二次来访」和「别人知道我的学号+姓名」
在信息层面是完全一样的。**这是设计的固有局限，不是实现 bug。**
真正解决它要靠**登录**（密码/短信/人脸），那是下一步的事。

把这个边界写进文档，比假装它不存在要好。

### 踩过的坑（都写进代码注释了）

**坑 1：对账公式算错**

`audit()` 最初写成 `Σbalance + Σfrozen`，但 `frozen` 是从 `balance` 划出来的，
不是额外资产 —— 等于把钱数了两遍，冻结 1000 却算出 2000。

**教训：先定死语义再写代码。** `balance` 是总资产（含冻结），
`frozen` 是其中被锁的部分，定了这个公式自然就对了。

**坑 2：争议能被当事人抹掉**

状态流转表最初写成简单的 `[目标状态, ...]` 数组，
结果 `disputed` 允许直接跳到 `completed`——**对方点一下"确认"就能把争议抹掉**。

修法：把「触发动作」也写进规则，`disputed → completed` 只允许 `resolve` 触发（管理员裁定）。

**教训：光约束"能去哪"，不够；还得约束"谁能推它去"。**

## 接口一览

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/publish` | 发布（**先过身份核验，未通过的返回 `needReview: true`**） |
| GET | `/api/trades` | 交易列表（支持 kind / status 筛选） |
| GET | `/api/trades/:id` | 单笔详情（含事件流水） |
| GET | `/api/identity/status?studentNo=` | 查某学号的身份状态 |
| GET | `/api/identity/pending` | 待审队列（给人工审核用，**真实项目要加鉴权**） |
| POST | `/api/identity/review` | 人工裁定（必须填说明，不能审自己） |
| GET | `/api/health` | 健康检查（含待审数） |

## 边界说明

**这是个人练手项目。平台不经手任何资金。**

- ✅ 可以：本地跑、给同学演示、放进作品集
- ❌ 不可以：让用户往平台充钱、提现、收保证金

原因：个人无法取得支付业务资质。这个项目里所有金额都只是
"双方约定价的记录"，钱在用户之间自行结算，平台不参与。
